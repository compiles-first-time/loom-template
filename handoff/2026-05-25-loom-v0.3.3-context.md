## Critical decisions + idioms NEW since 2026-05-20

These are additive to (not replacing) the prior handoff's "Critical decisions and idioms" section.

### Specialist-invocation discipline when registry is unavailable (ADR-0034)

The Ravenwise bootstrap surfaced the silent-degradation failure mode: the agent stamped 18 specialists, read the "RESTART CLAUDE CODE NOW" banner, and **kept working anyway as the "general builder"** — bypassing specialist consultation entirely. The output compiled, looked plausible, and passed surface checks. Discovery flow was never run. Hook capture never fired (CWD mismatch — see below). Zero events in the event log.

**The discipline** (ADR-0034 §A four-step check):

1. Check `.claude/agents/.last-discovered-at` vs session start time. Registry-stale = stamped this session.
2. If unavailable, choose: **(2a) restart path** — instruct architect to restart; **(2b) simulation path** — use the general-purpose `Agent` tool with each relevant specialist's SKILL.md content as the prompt. Path 2b was validated in real session (Agents A, B, C produced specialist-quality output) and is first-class, not a workaround.
3. **Log the simulation explicitly** — chat output is the audit surface when hooks aren't firing.
4. Per-session-per-write-class verification — no specialist context bleed.

**Bypassing both 2a and 2b without architect attestation = LR-05 violation** (operationalized under LR-05's best-current-call requirement).

### Hook-capture gap when CWD ≠ project directory

Loom's hooks load against the Claude Code session's CWD at startup. If the architect shells INTO a Loom project from a non-Loom CWD (e.g., `cd C:\Users\...\Internal Platform` then `cd C:\Users\...\ravenwise`), the hooks loaded for the original CWD don't fire on the Ravenwise tool calls. **Audit trail goes silent without warning.**

**Workaround until properly fixed**: open Claude Code IN the project directory (`code <project-root>` or set the working directory to the project root at session start). Future ADR will codify this; for now, ADR-0034 §C surfaces the gap to the architect proactively.

### MCP auth-target verification before write operations (Ravenwise Root cause 4)

MCP server credentials (PATs) are configured at the MCP-server level, not the project level. They travel with the session, not the project. An architect with multiple accounts on the same platform may have an MCP authed to the wrong account. **Silent wrong-account writes are the failure mode.**

**The discipline** (ADR-0036 §B step 3 + provisioning specialist PROV-EX-02):

Before ANY MCP write op against a credentialed service:
- Call the service's `list_organizations` / `whoami` / equivalent read-only call
- Surface the authenticated identity to the architect: *"The `<service>` MCP is authenticated as `<identity>`. Is this the intended account for this project? [y/N]"*
- Wait for explicit confirmation. "Continue" / "looks good" / silence are NOT sufficient
- Per-write-class verification (attesting for `create_project` doesn't extend to `create_org` or `delete_project`)

The Ravenwise session validated this: my `list_organizations` returned "ZD Digital Marketing" (an org Nick didn't intend for Ravenwise); his explicit "No — wrong account; stop" prevented a wrong-org `create_project` call.

### The four operation classes (provisioning specialist, ADR-0035 §A)

Per-platform playbooks categorize each operation:

- **Class A** — automated end-to-end (API or MCP). Specialist executes directly. Idempotent + cost-aware.
- **Class B** — browser-only at session start. No API path exists. Specialist DECLINES + batches into ONE architect handoff at session start (not one-step-at-a-time mid-session).
- **Class C** — browser-only just-in-time. Some operations only surface mid-execution (e.g., "add the prod URL to the OAuth client's authorized redirects" after first Vercel deploy). Decline + handoff with full context at that moment.

### Per-section dating in playbooks + matrix (ADR-0035 §B / ADR-0033 §A)

Some sections drift faster than others. Class B click sequences rebrand frequently (Google's "Cloud Console" → "Google Auth Platform" mid-2025); Class A API endpoints are more stable. **Per-section `<!-- last_verified: YYYY-MM-DD -->` markers** let the doctor's `playbook-freshness` check be precise about what's stale. Same precedent applies to matrix rows.

### Credential collection: dual-track architecture (ADR-0036)

**Primary path:** OS keyring via `@napi-rs/keyring`. Cross-platform: Windows Credential Manager (DPAPI), macOS Keychain, Linux Secret Service. Lazy-imported so the binding is optional. Service-key convention: `loom-<project-name>`. Account-key convention: `<platform>-<credential-type>`.

**Fallback path:** literal `.env.local` (always supported). Per-line detection: lines starting with `keyring:` resolve via keyring; everything else passes through. **No mode switch — both forms coexist within one `.env.local`.**

**Collection mechanism:** `scripts/collect-credentials.{sh,ps1}`. Stdin-only (never chat). Validates each credential via read-only pre-flight call. Account-attestation prompt (closes Root cause 4). Stores via keyring + writes `keyring:` reference to `.env.local`.

### Cascade-merge wrong-base failure mode (learned the hard way)

When merging cascade PRs via `gh pr merge`, **downstream PRs' bases must be re-targeted to main BEFORE merging** — otherwise each downstream PR merges into its declared sibling cascade branch instead of main. This bit the 2026-05-25 session: PR #30 merged correctly to main; PRs #31 + #32 merged into their cascade-base branches and stranded. Catchup PR #33 fixed it by cherry-picking.

**Two prevention strategies for future cascades:**
- (a) Re-target before each downstream merge: `gh pr edit <pr> --base main` after merging upstream
- (b) All cascade PRs target main directly from the start (loses cascade-branch visibility but eliminates wrong-base risk)

### Architect-attestation as bypass key for classifier-blocked actions

Per the existing handoff §"Anthropic CLI auto-mode classifier", `gh pr merge` from the Builder is classifier-blocked. **However:** explicit architect attestation in the conversation ("please take this message as approval to raise the PRs and do the merges") lifts the block for that session. Validated 2026-05-25 — 5 PRs merged via `gh pr merge` after the attestation.

This is per ADR-0034 §B bypass policy (now codified): the bypass requires explicit, on-the-record architect attestation naming the action being authorized.

## Open questions deferred to the business-Claude session

These are architect-level questions Nick may want to discuss early:

- **Token-cost design constraint for the RAG arc.** Loops that re-call LLMs amplify token spend. Should this be codified as a new constitutional invariant (e.g., LR-06)? Or remain a per-implementation discipline?
- **RAG vs alternative retrieval paradigms.** Current ADR-0003 specifies hybrid retrieval + RRF + rerank — best-current-call when authored. New evidence (GraphRAG, agentic RAG, late-interaction models like ColBERT v3) may supersede. Per LR-05.
- **Multi-account credential hygiene.** Ravenwise lives in one Supabase org; the MCP we tested with was authed to a different one. ADR-0036 §G handles per-project namespacing, but what about per-architect-account namespacing within a project? (Future-mature problem.)
- **When to write the next handoff doc.** Per ADR-0031 §A, triggers are: major-version PR cascade merged (RAG arc would qualify), new LR added, new Layer added, > 30 days + new ADR accepted. Don't let this slip.
