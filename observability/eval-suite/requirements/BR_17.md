# BR_17 — Requirements registers are checked, not trusted

> Register per [ADR-0046](../../../adr/0046-requirements-exceptions-testcase-registry.md),
> schema per [ADR-0061](../../../adr/0061-requirements-register-role-and-verifier-fields.md).
> Tests: [`scripts/lib/requirements-register.test.mjs`](../../../scripts/lib/requirements-register.test.mjs) — 33/33.

The ask: the 2026-08-13 harvest of nine registers found the format had **degraded on contact with use, unnoticed for a year** — five of twelve specified fields present in zero registers, exceptions attached to the requirement rather than the step in 8 of 9, and density decaying to zero (BR_12: four steps, no exceptions). Same root cause as ADR-0059/0060: **an unchecked convention drifts.** This register is itself written in the corrected schema, as the reference example.

|---|---|---|
| Exceptions attached to the requirement, not the step | 8 registers (BR_01, 06–11, 13) | requirements-analyst |

**Not automatable.** An agent rewriting exception IDs would be guessing which step each exception guards — exactly the invisible-reasonable-assumption failure the Requirements Analyst exists to prevent.
